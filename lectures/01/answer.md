- 講座に固有の質問（宿題の3レベル）へのモデルの回答（要約でよい）：
  講座の資料を知らないため、一般的なプログラミング講座を想定して「基礎（ベーシック）・応用（スタンダード）・発展（アドバンス）」の3段階だと推測して答えた。講座名も「AIエンジニア育成講座」と誤って解釈していた。

- 用語集の正しい意味と比べて気づいたこと：
  「3段階に分かれている」「基礎・発展という名前のレベルがある」点は合っていたが、2段階目は「応用」ではなく「実装」だった。また各レベルの中身も違い、正しくは基礎＝モデルやtemperatureを変えて出力を比較、実装＝ask.pyを会話履歴付きに改造、発展＝応答時間・トークン数を複数モデルで比較、という具体的な課題だった。モデルは知らない講座固有の情報でも「分からない」とは言わず、もっともらしい一般論を自信を持って答えており、ハルシネーションの典型例だと感じた。回答末尾で「教材に具体的な指定があればそれに従う」と注意書きしていた点は良かった。

## 宿題

- 取り組んだレベル：実装
- やったこと：
  - `app/ask.py` に `--chat` オプションを追加し、続けて質問できる対話モードを作った
  - 会話履歴は SDK の Chat 機能を使わず、`types.Content` のリストで自分で持つ形にした。
    質問のたびに user の発言を追加して履歴全体を `generate_content` に送り、
    返ってきた答えを role="model" として追加する
  - API エラーのときは、その質問を履歴から外して続けられるようにした
  - 各往復で入力・出力トークン数を表示するようにした
  - 自分で持つ形を選んだ理由：LLMのAPIは本来ステートレスで、「会話を覚えている」ように見えるのは履歴を毎回送っているからだという仕組みを自分の目で確認したかったため。また、エラー時に失敗した発言だけを履歴から外すなど、履歴の中身を自分で制御でき、送っているトークン量も把握しやすいと考えた。
- 結果（モデル：gemini-3.5-flash-lite）：
  - 対話モードで「私の名前はカリベです。」と伝えた後、「私の名前は何ですか?」と聞くと「カリベさんですよ！」と答えた
  - 1回だけ質問するモードで同じ質問をすると：「申し訳ありませんが、私にはあなたの名前がわかりません。教えていただけますか？」と答え、名前を答えられなかった
  - 入力トークン数は往復ごとに 8 → 59 → 73 → 102 と増えた（出力は 44 / 10 / 22 / 36）
  - 終了の言葉を「exit:」とコロン付きで入力したところ、終了せずにモデルへの質問として送られ、モデルは「さようなら」と返した
- 気づき・疑問：
  - 1回モードでは名前を答えられず、対話モードでは答えられた。同じモデル・同じ質問でも、履歴を送るかどうかだけで結果が変わることから、モデル自体は前の発言を記憶していないことが確認できた。
  - 入力トークン数の増え方を見ると、2往復目の59は「1往復目の質問8＋回答44＋新しい質問約7」とほぼ一致し、3・4往復目も同様に「前回までの入力＋前回の出力＋新しい質問」になっていた。モデルが会話を覚えているのではなく、履歴全体を毎回送り直しているだけだということが数字で確認できた。
  - そのため会話が長くなるほど入力トークンが積み上がり、コストや応答時間が増え、いずれはコンテキストの上限にも達する。長い対話では古い履歴を要約する・直近N往復だけ残すなどの工夫が必要になると思った。
  - 「exit:」で終了しなかったのは、終了判定を文字列の完全一致で行っていたため。前後の空白や記号を取り除く、大文字小文字をそろえるなど入力を正規化してから判定すべきだった。ユーザーは開発者の想定どおりに入力しないという、講義の「開発者は平均的なユーザーではない」という話を実感した。
  - 疑問：SDKのChat機能を使った場合も内部では同じように履歴を全部送っているのか。また、履歴を削る場合にどの情報を残すと会話の質が保てるのか。
